## Thread safety

Until the items below are done, don't add, remove or free the same listener from two threads at once. Adding one listener to two daemons from two threads is already safe, because `monero_daemon_add_listener()` holds `registration_mutex`.

- [ ] **monero-cpp: split `remove_listener()` in two steps.** `remove_listener()` erases the listener and waits for the callbacks in flight, in one call, and the wait is private. monero-c can't keep its lock across the wait, because a callback may call `monero_daemon_remove_listener()` on the same listener and the lock would deadlock. Plan: expose an erase-only call (for example `detach_listener()`) and make `wait_for_listener_callbacks_idle()` public. Needs an upstream change or a fork, then a bump of the monero-cpp submodule.
- [ ] **monero-c: keep `registered_with` in step with the daemon's listener set.** `monero_daemon_remove_listener()` erases the listener, then resets `registered_with`. If `monero_daemon_add_listener()` runs on the same daemon in between, it finds the listener still tracked and inserts it again, and the reset then leaves it untracked. `monero_daemon_listener_free()` won't unregister it, and the daemon calls back into freed memory. Plan: erase and reset under `registration_mutex`, and wait for the callbacks after the lock is released. Depends on the monero-cpp split above.
- [ ] **monero-c: decide what `monero_daemon_add_listener()` does during a removal.** While a removal waits for callbacks, a new add of the same listener should either wait for the removal to finish or fail. Decide which, and document it in `monero_c_daemon.h`.
- [ ] **monero-c: test the race.** The C test suite has no threads. Add a test that runs add, remove and free of one listener from two threads, and run it under ThreadSanitizer in CI. Until then the race is covered only by reasoning.
- [ ] **Remove the thread safety warning from `README.md`** once the items above are done.

## Wallet API

The core of `monero_wallet` is in `src/wallet/`: creation from random seed, seed, keys and file, save, close, free, the getters for address, keys, height and balances, and the listener handles. The unit tests cover these without a daemon. `monero_c_wallet_offline_unit_tests` covers the methods that need no daemon: address book, accounts, attributes, notes, key images, outputs, password and daemon connection settings. `monero_c_wallet_keys_unit_tests` covers the keys-only wallet after monero-python's `test_monero_wallet_keys.py`, minus the tests that need a daemon. Its test vectors are the public, funds-free wallet of monero-python's `tests/config/config.ini`. Full wallets don't support `get_subaddress()` and the account tags, and the errors come from monero-cpp. The public methods of monero-cpp's base, full, keys-only and RPC classes are exposed, except the in-memory and shutdown methods, which are left out on purpose below. `monero_c_wallet_multisig_unit_tests` covers the 2 of 3 key exchange without a daemon. `monero_c_wallet_integration_tests` covers the daemon methods, the balances, the history, the reserve proofs and the RPC wallets, against a regtest node and a monero-wallet-rpc server.

- [ ] **monero-c: more send tests on regtest.** The integration test mines 100 blocks, creates a transaction, relays it from its JSON and mines it, and checks the tx key, the tx and spend proofs, and `sweep_output()` and `sweep_unlocked()` without relay. The outputs of the miner are RingCT outputs, and a ring takes its decoys only from unlocked outputs. The coinbase outputs unlock after 60 blocks, so a ring of 16 needs about 76 blocks, and the test mines 100. Still open on the same chain: the `on_output_spent` callback, the key image import into a second wallet, and a sweep that is relayed.
- [ ] **monero-c: multisig transactions.** The multisig test stops at the key exchange and the import. `sign_multisig_tx_hex()` and `submit_multisig_tx_hex()` need a 2 of 3 wallet with funds. The regtest chain can fund one now (see the send tests above), so the test can move to the integration suite.
- [ ] **monero-cpp: use the ring size of the config.** `create_txs()`, `create_txs_all()` and `create_tx_single()` in `monero_wallet_full.cpp` call wallet2 with `adjust_mixin(0)`. On hard fork 16 wallet2's minimum and maximum ring are both 16, so `adjust_mixin` always returns 16 and `ringSize` in `monero_tx_config` is only written back in the result. Plan: pass the configured ring size minus one to wallet2 in those three functions, and throw when wallet2 would use another ring, instead of clamping it silently. Then add an integration test that a `ringSize` of 16 gives 16 in the result, and that another value fails. Until then, the ring is 16.
- [ ] **monero-c: review the docs of the wallet against monero-cpp's style.** Check the docstrings in `monero_c_wallet.h`, the comments in `src/wallet/` and the test comments. Docstrings are short and open with a verb. Inline comments are lowercase, without a final period, and there are no semicolons. Keep the `@param` and `@return` structure. Remove repeated boilerplate and anything that reads as generated.
- [x] **monero-c: check the wallet RPC part in CI.** `docker-compose.yml` has a `wallet_rpc` service that shares the network of the node, because the tests give the wallet RPC the daemon URI `http://127.0.0.1:18081`, and the integration job sets `MONERO_C_TEST_WALLET_RPC_URI`. The integration job of the Tests run for PR #9 passes: daemon 183/183, wallet 187/187 with the RPC part.
- [ ] **monero-c: wallet listener race.** The same race as the daemon listeners: adding and removing one listener from two threads can leave it untracked, and free then doesn't unregister it. `monero_wallet_full::notify_listeners()` holds monero-cpp's listener lock while it calls the callbacks, and a callback may call `monero_wallet_add_listener()` or `monero_wallet_remove_listener()` on the same listener. So the remove step can't run under `registration_mutex`. The add step reserves the wallet under the lock and calls monero-cpp outside it. Plan: the same erase-and-reset split as the daemon, if monero-cpp allows it without the lock. Until then, don't add, remove or free the same listener from two threads at once.
- [x] **monero-c: wallet README and docs.** The README has a sample with a daemon, a full wallet, a listener and an RPC wallet, the handles in Memory Ownership and the wallet rules in Thread Safety. The networks are in the docs of `monero_utils_network_type` and `monero_wallet_create_random()`.

Left out on purpose: `open_wallet_data()`, `get_keys_file_buffer()` and `get_cache_file_buffer()` open and export a full wallet from memory instead of files, and `request_shutdown()` prepares a close while other calls are still running on the wallet. The bindings don't need them. A binding saves, opens and closes a wallet with `monero_wallet_save()`, `monero_wallet_open()` and `monero_wallet_close()`, which keep the keys and the wallet file next to the path. The buffer methods would add three functions and a second storage path that every caller has to handle, and none of the planned bindings (Dart, C#, Kotlin) needs it, because they run on systems with a file system. Revisit this for a target without one. `request_shutdown()` only matters when another thread is inside a call on the same wallet. The C handle must not be used from two threads at once, so a binding never reaches that case. `monero_wallet_close()` calls `request_shutdown()` first and then waits for the sync thread, so a binding gets the same effect from `close()`. Phase B exposes `stop_syncing()` to stop a sync without closing the wallet.

## ABI safety

- [ ] **monero-cpp: free the wallet when a factory throws.** `open_wallet()`, the `create_wallet*()` functions of `monero_wallet_full` and the factories of `monero_wallet_keys` allocate the wallet with a raw `new`, so an exception after it leaks the wallet and its `wallet2`. LeakSanitizer finds it on every `monero_wallet_open()` with a wrong password, about 200 KB each time. Plan: hold the wallet in a `std::unique_ptr` and `release()` it on return. Then remove the line in `tests/c/sanitizers/lsan.supp`.
- [ ] **monero-c: hide the static archives' symbols on macOS and Windows.** On Linux `-Wl,--exclude-libs,ALL` keeps the exports to the C ABI: 288 functions. Measured on the `Monero.Native.0.1.0-alpha.1` package of PR #12: the macOS libraries export 19,021 (arm64) and 23,086 (x64) symbols, about 12,000 of them C functions of OpenSSL, and the x64 one also exports the three `monero_crypto_amd64_64_24k_*` assembly helpers (291 `monero_*` symbols instead of 288). macOS binds symbols per library (two-level namespace), so this is less harmful than on Linux, but it widens the ABI. Plan: pass an export list to ld64, `-Wl,-exported_symbol,_monero_*`, and check it in CI with `nm -gU`. The Windows DLL exports the 288 functions and 1,099 Boost template symbols that Boost marks `BOOST_SYMBOL_EXPORT`, and no C symbols of OpenSSL or libsodium, so it is low priority. `tests/c/abi/check_symbols.cmake` runs on Linux only.
