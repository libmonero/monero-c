## Thread safety

Until the items below are done, don't add, remove or free the same listener from two threads at once. Adding one listener to two daemons from two threads is already safe, because `monero_daemon_add_listener()` holds `registration_mutex`.

- [ ] **monero-cpp: wake `wait_for_next_block()` of the full wallet from `request_shutdown()`.** The wait ends only with a block: `request_shutdown()`, `stop_syncing()` and `close()` leave it blocked, so a program that has to stop leaves its thread behind. It also waits on a condition variable with no predicate, so a block that arrives between `add_listener()` and the wait wakes nobody, and `last_height` is not initialized, so a spurious wake-up returns garbage (the daemon's `wait_for_next_block_header()` already has the predicate and a listener guard). Plan: a predicate, a flag that `request_shutdown()` sets and notifies, and an error for the call that it wakes. monero-c builds `monero_wallet_wait_for_next_block_timeout()` on its own waiter and calls the plain wait directly; it tried a cancel of the plain wait on `monero_wallet_request_shutdown()` and dropped it, because the fix belongs to monero-cpp. Once it is there, the docs of `monero_wallet_wait_for_next_block()` and `docs/thread-safety.md` can say that `monero_wallet_request_shutdown()` wakes it.
- [ ] **monero-cpp: `get_listeners()` gives raw pointers.** `monero_wallet::get_listeners()` and `monero_daemon::get_listeners()` return a copy of the set of `monero_wallet_listener*`, which a listener that another thread removes and frees leaves dangling. monero-c keeps a registry of its own handles to look them up without reading them (`core_of()` in `src/wallet/monero_c_wallet.cpp`, `daemon_listener_registry` in the daemon), and any other consumer that frees listeners from a thread has the same problem. Plan: return `shared_ptr`s, or take the listener lock for a visit function.
- [ ] **monero-cpp: typed exceptions for the failures that a program has to tell apart.** `monero_last_error_code()` comes from the type of the exception, and monero-cpp throws its plain `monero_error` or `std::runtime_error` for most of them, so these are all `MONERO_ERROR_GENERIC` (probed on 2026-11-10 against a closed port): a daemon that doesn't answer (`Network error: no response from http://127.0.0.1:1/json_rpc (timeout: 1000ms)`), a wallet that can't reach its daemon (`Wallet is not connected to daemon`), a file that doesn't exist (`file not found "/nonexistent/x.keys"`), a mnemonic that isn't valid (`Invalid mnemonic`), a wallet that is closed (`Wallet is closed`) and a tx without destinations. A binding that throws typed exceptions has to match the text. Plan: subclasses of `monero_error` (a network error, a file error, an invalid argument, a closed wallet) or a code member in it, thrown at those places in monero-cpp. monero-c then catches them in `set_last_error_from_current_exception()` and `MONERO_ERROR_IO` covers the network error again, with one more value for the closed wallet if a binding needs it.
- [ ] **monero-cpp: split `remove_listener()` in two steps.** `remove_listener()` erases the listener and waits for the callbacks in flight, in one call, and the wait is private. monero-c can't keep its lock across the wait, because a callback may call `monero_daemon_remove_listener()` on the same listener and the lock would deadlock. Plan: expose an erase-only call (for example `detach_listener()`) and make `wait_for_listener_callbacks_idle()` public. Needs an upstream change or a fork, then a bump of the monero-cpp submodule.
- [ ] **monero-c: keep `registered_with` in step with the daemon's listener set.** `monero_daemon_remove_listener()` erases the listener, then resets `registered_with`. If `monero_daemon_add_listener()` runs on the same daemon in between, it finds the listener still tracked and inserts it again, and the reset then leaves it untracked. `monero_daemon_listener_free()` won't unregister it, and the daemon calls back into freed memory. Plan: erase and reset under `registration_mutex`, and wait for the callbacks after the lock is released. Depends on the monero-cpp split above.
- [ ] **monero-c: decide what `monero_daemon_add_listener()` does during a removal.** While a removal waits for callbacks, a new add of the same listener should either wait for the removal to finish or fail. Decide which, and document it in `monero_c_daemon.h`.
- [ ] **monero-c: test the race.** `monero_c_threads_unit_tests` adds, removes and frees different listeners of one daemon from six threads, calls `monero_daemon_get_listeners()` meanwhile, adds one wallet listener to two wallets from two threads, and shares a connection and a daemon between threads. It is clean under AddressSanitizer and LeakSanitizer, and it found the read of freed memory in `monero_daemon_get_listeners()` and the leak of the scratchpad of the password hash, which are fixed. Still missing: a test that runs add, remove and free of the same listener from two threads, which races today and is what the items above are for, and a ThreadSanitizer job in CI. With monero_c built with `-fsanitize=thread` (the static archives of monero-project aren't instrumented) and started with `setarch -R`, which kernels with high address randomization need, the unit tests of the daemon, the connection and the offline wallet are clean, and the threads test reports four races, none in monero_c: the list of languages of the mnemonics, the lock of the random generator and the hash table of OpenSSL, all of them started by `monero_wallet_create_from_seed()` on several threads, and the shared pointer of a boost regex. They are in code that TSan sees from one side only, so they may be false reports, and the first two may be lazy initializations of monero-project without a lock. A job needs a suppression file for them, or the archives built with the sanitizer.
- [ ] **Remove the thread safety warning from `README.md`** once the items above are done.

## ABI safety

- [ ] **monero-cpp: free the wallet when a factory throws.** `open_wallet()`, the `create_wallet*()` functions of `monero_wallet_full` and the factories of `monero_wallet_keys` allocate the wallet with a raw `new`, so an exception after it leaks the wallet and its `wallet2`. LeakSanitizer finds it on every `monero_wallet_open()` with a wrong password, about 200 KB each time. Plan: hold the wallet in a `std::unique_ptr` and `release()` it on return. Then remove the line in `tests/c/sanitizers/lsan.supp`.
- [ ] **monero-c: hide the Boost symbols of the Windows DLL.** The Windows DLL exports the functions of the C ABI and 1,099 Boost template symbols that Boost marks `BOOST_SYMBOL_EXPORT`, and no C symbols of OpenSSL or libsodium, so it is low priority. A `.def` file with the functions of `monero_c.symbols` would do it, and `check_symbols.cmake` would read the DLL with `objdump -p`. Checked again: a `.def` file would not do it. The manual of `ld` says that when symbols are exported by a `.def` file or by an attribute, the linker exports nothing else, and the 1,099 symbols are exported by attribute (`BOOST_SYMBOL_EXPORT` is `__attribute__((__dllexport__))` for GCC on Windows, set in `boost/config/compiler/gcc.hpp` with no `#ifndef`), so the `.def` file adds to them. `--exclude-symbols` only applies to the symbols exported automatically. Defining `BOOST_SYMBOL_EXPORT` empty for the objects of monero-c would not reach the archives of monero-cpp and monero-project, which carry their own exports. Left open: it needs a change in the build of the archives, or a post-link step that rewrites the export table.
- [ ] **monero-cpp: limit the nesting of the JSON it parses.** `deserialize_rpc_response()` parses every response with `gen_utils::deserialize()`, which calls boost's `read_json()`, and that parser recurses once per level. A node that answers a request with 200 KB of `[[[[...` (100000 levels) overflows the 8 MB stack and ends the process. Tested with `monero_rpc_connection_send_json_request()` and `monero_daemon_get_info()` against a script that answers every request with nested arrays: 20000 levels pass and 100000 crash. monero-c limits the JSON that a caller passes to 64 levels, but it can't reach a response, which monero-cpp parses. A thread with a 1 MB stack, which is the default on Windows, crashes with a response of 8 KB: 4000 levels pass and 8000 crash. `master` at 750fe70 has no limit either. Plan: throw "Invalid JSON" above a fixed depth in `gen_utils::deserialize()`, and add a test with the fake server of `monero_c_rpc_connection_unit_tests`. Mutating the answers of a node found no other crash, so this one is the only known way for a node to end the process.
- [ ] **monero-cpp: `get_blocks_by_range()` lists every height first.** The loop `for (height = start; height <= end; height++)` never ends when `end` is `UINT64_MAX`, and it fills a vector with each height before the first request, so a wide range uses all the memory. monero-c refuses a range of more than 100000 blocks (`MAX_BLOCKS_BY_RANGE` in `monero_c_daemon.cpp`). Plan: send the heights in chunks, as `get_blocks_by_range_chunked()` does, and check the end against the height of the chain. Then the limit of monero-c can go.
- [ ] **monero-project: `wipeable_string::split()` takes quadratic time.** `epee::wipeable_string::split()`, which `get_is_old_style_seed()` and `words_to_bytes()` call, appends a word one character at a time, and each append reallocates, copies and wipes the buffer. A mnemonic of 100 KB takes 0.8 s to check and one of 400 KB takes 15 s. monero-c rejects a mnemonic of more than 4096 bytes (`MAX_MNEMONIC_LENGTH` in `monero_c_common.h`), which is far above any valid one. Plan: report it upstream. The limit stays, because it also keeps a megabyte of text away from the check.
- [ ] **monero-c: wallet paths with non-ASCII characters on Windows.** monero-project activates UTF-8 for Boost.Filesystem on Windows in `Wallet::init()` and in `simplewallet` (`boost::locale::generator().generate("")` and `boost::filesystem::path::imbue()`), and neither monero-cpp nor monero-c does. A UTF-8 path with a character outside the ANSI code page, such as a user name with an accent, is probably read as ANSI there. It works on Linux, checked from C# with an accent, kanji and an emoji (`CreatesAndReopensAWalletAtANonAsciiPath`, which returns early on Windows). Not tested on Windows. Plan: run the test on Windows, and if it fails, set the locale once for `_WIN32` in monero-c or in monero-cpp (Boost.Locale is already one of the linked components), then check `monero_wallet_exists()`, `monero_wallet_open()`, `monero_wallet_move_to()` and the logging path.
- [ ] **monero-cpp: make `monero_utils::free()` release the daemon models and the input query.** `free(block)` resets `m_block` of the txs in `m_txs`, and of a wallet tx its transfers, outputs, inputs and tx set, and of a tx query its transfer and output query. It leaves the miner tx of the block, the inputs and outputs of a plain `monero_tx` as `monero_daemon_rpc` builds it, and the input query of a tx query, so a caller of `get_block_by_height()` or `get_tx()` still leaks after calling it. monero-c has `release_models()` for the daemon models and resets the input query itself, until this is fixed.
- [ ] **monero-cpp: free the txs that `get_txs()` filters out.** `get_txs_aux()` builds the txs, then erases the ones that don't meet a transfer, input or output query, and doesn't free them, so each keeps its transfers, outputs and block. `monero_wallet_get_txs()` with `{"inputQuery":{"isSpent":true}}` on a wallet whose txs all fail the query keeps 9.7 KB for 5 txs and 243 KB for 100 on every call (LeakSanitizer with the slow unwinder points to `build_tx_with_incoming_transfer()` called from `get_txs_aux()`). Plan: call `monero_utils::free()` on the tx that the loop erases. monero-java has the same leak.
- [ ] **monero-cpp: free the copy of the query in `get_outputs()`.** `get_outputs_aux()` copies the tx query of the output query, and the copy of an input query points back at the copy of the tx query, so a query with an input query in its `txQuery`, such as `{"txQuery":{"inputQuery":{"isSpent":true}}}`, keeps about 1.5 KB on every call (31 KB for 20 calls under LeakSanitizer). A query without an input query keeps nothing. monero-c can't release the copy, which is local to the function. Plan: reset the links of the copy before `get_outputs_aux()` returns, as `monero_utils::free()` does for the other queries.
