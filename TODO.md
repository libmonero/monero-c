## Thread safety

Until the items below are done, don't add, remove or free the same listener from two threads at once. Adding one listener to two daemons from two threads is already safe, because `monero_daemon_add_listener()` holds `registration_mutex`.

- [ ] **monero-cpp: split `remove_listener()` in two steps.** `remove_listener()` erases the listener and waits for the callbacks in flight, in one call, and the wait is private. monero-c can't keep its lock across the wait, because a callback may call `monero_daemon_remove_listener()` on the same listener and the lock would deadlock. Plan: expose an erase-only call (for example `detach_listener()`) and make `wait_for_listener_callbacks_idle()` public. Needs an upstream change or a fork, then a bump of the monero-cpp submodule.
- [ ] **monero-c: keep `registered_with` in step with the daemon's listener set.** `monero_daemon_remove_listener()` erases the listener, then resets `registered_with`. If `monero_daemon_add_listener()` runs on the same daemon in between, it finds the listener still tracked and inserts it again, and the reset then leaves it untracked. `monero_daemon_listener_free()` won't unregister it, and the daemon calls back into freed memory. Plan: erase and reset under `registration_mutex`, and wait for the callbacks after the lock is released. Depends on the monero-cpp split above.
- [ ] **monero-c: decide what `monero_daemon_add_listener()` does during a removal.** While a removal waits for callbacks, a new add of the same listener should either wait for the removal to finish or fail. Decide which, and document it in `monero_c_daemon.h`.
- [ ] **monero-c: test the race.** `monero_c_threads_unit_tests` adds, removes and frees different listeners of one daemon from six threads, calls `monero_daemon_get_listeners()` meanwhile, adds one wallet listener to two wallets from two threads, and shares a connection and a daemon between threads. It is clean under AddressSanitizer and LeakSanitizer, and it found the read of freed memory in `monero_daemon_get_listeners()` and the leak of the scratchpad of the password hash (see the items below). Still missing: a test that runs add, remove and free of the same listener from two threads, which races today and is what the items above are for, and a ThreadSanitizer job in CI. With monero_c built with `-fsanitize=thread` (the static archives of monero-project aren't instrumented) and started with `setarch -R`, which kernels with high address randomization need, the unit tests of the daemon, the connection and the offline wallet are clean, and the threads test reports four races, none in monero_c: the list of languages of the mnemonics, the lock of the random generator and the hash table of OpenSSL, all of them started by `monero_wallet_create_from_seed()` on several threads, and the shared pointer of a boost regex. They are in code that TSan sees from one side only, so they may be false reports, and the first two may be lazy initializations of monero-project without a lock. A job needs a suppression file for them, or the archives built with the sanitizer.
- [x] **monero-c: write down the one-listener-per-wallet rule for bindings.** monero-java adds one native listener to a wallet when its first Java listener arrives, keeps it until `close()` has drained the callbacks, and fans out in Java (`setListenerJni()` returns the existing one). A binding that does the same never adds, removes or frees a listener while a callback may run, so the races above don't reach it. The Thread Safety rules of the README and the rules of `packaging/dotnet-core/README.md` say it. That `monero_wallet_close()` waits for the callbacks is in monero-cpp: `close()` requests the shutdown, joins the sync thread, takes the sync mutex and resets the listener of wallet2, which waits for the queued notifications. `monero_wallet_listener_free()` after the close succeeds without an error, and either order with `monero_wallet_free()` works (checked under ASan, and the offline test closes, frees the listener and frees the wallet).
- [x] **monero-c: `monero_daemon_get_listeners()` read freed listeners.** It copied the set of monero-cpp, which holds the adapters inside the handles, and read each one with `dynamic_cast` to find its handle. Another thread that freed a listener after the copy, which the headers allow ("different listeners on one daemon can be managed from different threads"), made that a read of freed memory, and `monero_c_threads_unit_tests` crashed in `__dynamic_cast` within a second. Each daemon handle now keeps the list of the handles that were added to it, under a mutex, and `get_listeners()` copies that list and reads no listener. `monero_daemon_listener_free()`, `monero_daemon_remove_listener()` and `monero_daemon_remove_listeners()` keep it in step. The wallet has the same loop in `monero_wallet_remove_listeners()`, but a wallet handle can't be used from two threads, so the free of another listener can't run meanwhile. `monero_daemon_remove_listeners()` also left the link of each listener to its daemon, so a listener that it removed couldn't be added to another daemon ("already registered with another daemon"), and `monero_daemon_add_listener()` now asks the set of that daemon.
- [ ] **Remove the thread safety warning from `README.md`** once the items above are done.

- [ ] **monero-c: hide the Boost symbols of the Windows DLL.** The Windows DLL exports the functions of the C ABI and 1,099 Boost template symbols that Boost marks `BOOST_SYMBOL_EXPORT`, and no C symbols of OpenSSL or libsodium, so it is low priority. The manual of `ld` says that when symbols are exported by a `.def` file or by an attribute, the linker exports nothing else, and the 1,099 symbols are exported by attribute (`BOOST_SYMBOL_EXPORT` is `__attribute__((__dllexport__))` for GCC on Windows, set in `boost/config/compiler/gcc.hpp` with no `#ifndef`), so the `.def` file adds to them. `--exclude-symbols` only applies to the symbols exported automatically. - [ ] **monero-cpp: limit the nesting of the JSON it parses.** `deserialize_rpc_response()` parses every response with `gen_utils::deserialize()`, which calls boost's `read_json()`, and that parser recurses once per level. A node that answers a request with 200 KB of `[[[[...` (100000 levels) overflows the 8 MB stack and ends the process. Tested with `monero_rpc_connection_send_json_request()` and `monero_daemon_get_info()` against a script that answers every request with nested arrays: 20000 levels pass and 100000 crash. monero-c limits the JSON that a caller passes to 64 levels, but it can't reach a response, which monero-cpp parses. - [ ] **monero-cpp: `get_blocks_by_range()` lists every height first.** The loop `for (height = start; height <= end; height++)` never ends when `end` is `UINT64_MAX`, and it fills a vector with each height before the first request, so a wide range uses all the memory. monero-c refuses a range of more than 100000 blocks (`MAX_BLOCKS_BY_RANGE` in `monero_c_daemon.cpp`). - [ ] **monero-project: `wipeable_string::split()` takes quadratic time.** `epee::wipeable_string::split()`, which `get_is_old_style_seed()` and `words_to_bytes()` call, appends a word one character at a time, and each append reallocates, copies and wipes the buffer. - [x] **monero-c: call the wallet callbacks without the lock of the wallet.** `monero_wallet_full::notify_listeners()` calls the callbacks while a sync holds the lock of the wallet. A callback that calls `monero_wallet_get_balance()`, `monero_wallet_get_unlocked_balance()`, `monero_wallet_get_txs()`, `monero_wallet_get_outputs()` or `monero_wallet_get_accounts()` on its wallet waits for that lock forever, and then `monero_wallet_remove_listener()` and `monero_wallet_stop_syncing()` wait for the callback. The header and the README tell callers to copy the arguments and call the wallet from another thread, which is what a C# binding has to do. Plan: put the events in a queue that a thread of monero-c delivers without any lock, copy the strings, and let `monero_wallet_remove_listener()` and `monero_wallet_listener_free()` wait for the queue unless they are called from a callback. It touches the same code as the listener race items above. - [ ] **monero-c: wallet paths with non-ASCII characters on Windows.** monero-project activates UTF-8 for Boost.Filesystem on Windows in `Wallet::init()` and in `simplewallet` (`boost::locale::generator().generate("")` and `boost::filesystem::path::imbue()`), and neither monero-cpp nor monero-c does. - [ ] **monero-cpp: make `monero_utils::free()` release the daemon models and the input query.** `free(block)` resets `m_block` of the txs in `m_txs`, and of a wallet tx its transfers, outputs, inputs and tx set, and of a tx query its transfer and output query. - [ ] **monero-cpp: free the txs that `get_txs()` filters out.** `get_txs_aux()` builds the txs, then erases the ones that don't meet a transfer, input or output query, and doesn't free them, so each keeps its transfers, outputs and block. `monero_wallet_get_txs()` with `{"inputQuery":{"isSpent":true}}` on a wallet whose txs all fail the query keeps 9.7 KB for 5 txs and 243 KB for 100 on every call (LeakSanitizer with the slow unwinder points to `build_tx_with_incoming_transfer()` called from `get_txs_aux()`). - [ ] **monero-cpp: free the copy of the query in `get_outputs()`.** `get_outputs_aux()` copies the tx query of the output query, and the copy of an input query points back at the copy of the tx query, so a query with an input query in its `txQuery`, such as `{"txQuery":{"inputQuery":{"isSpent":true}}}`, keeps about 1.5 KB on every call (31 KB for 20 calls under LeakSanitizer). - [x] **monero-c: free the scratchpad of the password hash when a thread ends.** monero-project allocates 2 MB for the first password hash of a thread, in a thread-local that only `slow_hash_free_state()` frees, and it calls that on its own threads. - [x] **monero-c: refuse a period of 0 or one that doesn't fit.** monero-cpp waits for the poll period of a daemon or an RPC wallet and for the sync period of a wallet with `boost::posix_time::milliseconds(long)`.
