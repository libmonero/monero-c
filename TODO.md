## Thread safety

Until the items below are done, don't add, remove or free the same listener from two threads at once. Adding one listener to two daemons from two threads is already safe, because `monero_daemon_add_listener()` holds `registration_mutex`.

- [ ] **monero-cpp: split `remove_listener()` in two steps.** `remove_listener()` erases the listener and waits for the callbacks in flight, in one call, and the wait is private. monero-c can't keep its lock across the wait, because a callback may call `monero_daemon_remove_listener()` on the same listener and the lock would deadlock. Plan: expose an erase-only call (for example `detach_listener()`) and make `wait_for_listener_callbacks_idle()` public. Needs an upstream change or a fork, then a bump of the monero-cpp submodule.
- [ ] **monero-c: keep `registered_with` in step with the daemon's listener set.** `monero_daemon_remove_listener()` erases the listener, then resets `registered_with`. If `monero_daemon_add_listener()` runs on the same daemon in between, it finds the listener still tracked and inserts it again, and the reset then leaves it untracked. `monero_daemon_listener_free()` won't unregister it, and the daemon calls back into freed memory. Plan: erase and reset under `registration_mutex`, and wait for the callbacks after the lock is released. Depends on the monero-cpp split above.
- [ ] **monero-c: decide what `monero_daemon_add_listener()` does during a removal.** While a removal waits for callbacks, a new add of the same listener should either wait for the removal to finish or fail. Decide which, and document it in `monero_c_daemon.h`.
- [ ] **monero-c: test the race.** No test uses a listener from two threads. Add a test that runs add, remove and free of one listener from two threads, and run it under ThreadSanitizer in CI. The unit tests that exist run clean under ThreadSanitizer, with monero_c built with `-fsanitize=thread` (the static archives of monero-project aren't instrumented) and started with `setarch -R`, which kernels with high address randomization need. The race itself is covered only by reasoning.
- [ ] **monero-c: write down the one-listener-per-wallet rule for bindings.** monero-java adds one native listener to a wallet when its first Java listener arrives, keeps it until `close()` has drained the callbacks, and fans out in Java (`setListenerJni()` returns the existing one). A binding that does the same never adds, removes or frees a listener while a callback may run, so the races above don't reach it. Put it in the thread safety rules of the README and of `packaging/dotnet-core/README.md`.
- [ ] **Remove the thread safety warning from `README.md`** once the items above are done.

## ABI safety

- [ ] **monero-c: release the models after serializing them.** The calls that return a transaction, a block, an output or a transfer serialize a graph of monero-cpp models, and the models point to their parents with `shared_ptr` (a tx to its block, an input or an output to its tx, a transfer to its tx, a tx to its tx set). Nothing in such a graph is freed unless the pointers are reset, so every call keeps its result. monero-java calls `monero_utils::free()` after it serializes (`monero_jni_bridge.cpp`, since 2023), and monero-c never does. Measured with the allocated bytes of AddressSanitizer after 20 calls on a regtest node, with a wallet of 100 transactions: `monero_wallet_get_txs()` and `monero_wallet_get_transfers()` keep 194 KB per call, `monero_wallet_get_outputs()` 217 KB, `monero_wallet_sweep_unlocked()` 254 KB, `monero_wallet_create_tx()`, `monero_wallet_create_txs()` and `monero_wallet_describe_tx_set()` 19 KB, `monero_daemon_get_block_by_height()` 2.2 KB and `monero_daemon_get_blocks_by_range()` of 39 blocks 72 KB. LeakSanitizer on the two integration suites reports 1.1 MB (wallet) and 27 KB (daemon). Plan: after the JSON is built, free the results and the parsed queries with `monero_utils::free()` for the wallet models, as the bridge does, and with a release of the daemon models in `monero_c_daemon.cpp`, because `monero_utils::free()` resets the txs of a block and not its miner tx or the inputs and outputs of a plain tx.
- [ ] **monero-c: keep the block and the tx in the JSON of the wallet and the daemon.** Each result is serialized alone with `serialize()`, which leaves out the pointers to the parent, so the JSON lacks context that the monero-cpp models have. Measured on regtest: `monero_wallet_get_txs()` has no height, timestamp or block hash, `monero_wallet_get_transfers()` and `monero_wallet_get_outputs()` have no hash of their tx, `on_output_received` gets `{amount, accountIndex, subaddressIndex}` and nothing else (the JNI listener of monero-java gets the height, the tx hash, the version, the unlock time and the locked flag), `monero_daemon_get_tx()` has no height, and on a view-only wallet `monero_wallet_create_tx()`, `monero_wallet_sweep_unlocked()` and `monero_wallet_sweep_dust()` return no `unsignedTxHex`, which is in the tx set, and only `monero_wallet_create_txs()` returns the set, so an offline signer can't sign them. The queries have a gap too: `monero_wallet_get_outputs()` ignores `txQuery` (`{"txQuery":{"isLocked":true}}` and `false` both return all 70 outputs of the test wallet) and `monero_wallet_get_transfers()` fails with "txQuery deserialization not implemented", so the filters of the tx are only reachable through `monero_wallet_get_txs()`. Plan: the protocol of monero-java and monero-ts, which the C# binding already expects (`MoneroWalletData.Blocks`): results as `{"blocks":[...]}` from `monero_utils::get_blocks_from_txs()`, `get_blocks_from_transfers()` and `get_blocks_from_outputs()`, `{"txSets":[...]}` for the creates and the sweeps, the tx in the payload of the listener, and the queries parsed with `deserialize_from_block()`. The order of the txs is lost for a query by hash, so the binding sorts them, as monero-java does. It changes the JSON of the ABI, so do it before the first release.
- [ ] **monero-c: find the CA certificates of the system.** The static OpenSSL has the directory of its build in the binary, read with `strings` on the libraries of the Build run of `main`: `/etc/ssl` on Linux, `/opt/homebrew/etc/openssl@3` (arm64) and `/usr/local/etc/openssl@3` (x64) on macOS. monero-project verifies with `set_default_verify_paths()`, so on a Mac without that Homebrew prefix, and on a distribution with another layout, a daemon with a certificate of a CA should fail the verification (taken from the binaries, not tried with a handshake). Windows is fine, because epee reads the root store of the system. monero-java sets `SSL_CERT_FILE` and `SSL_CERT_DIR` when its library is loaded (`set_default_ssl_cert_paths()` in `monero_jni_bridge.cpp`), from the usual locations, unless the user set them or the default file exists and is not empty. Plan: the same, once, before the first connection, and a test against a daemon behind TLS on a macOS runner.
- [ ] **monero-cpp: free the wallet when a factory throws.** `open_wallet()`, the `create_wallet*()` functions of `monero_wallet_full` and the factories of `monero_wallet_keys` allocate the wallet with a raw `new`, so an exception after it leaks the wallet and its `wallet2`. LeakSanitizer finds it on every `monero_wallet_open()` with a wrong password, about 200 KB each time. Plan: hold the wallet in a `std::unique_ptr` and `release()` it on return. Then remove the line in `tests/c/sanitizers/lsan.supp`.
- [ ] **monero-c: wipe the secrets that leave the library.** `monero_wallet_get_seed()`, the key getters and the wallet config copy seeds and keys into `std::string`s and into `malloc`ed output, and `monero_utils_free()` is a plain `free()`, so they stay in freed memory. monero-cpp keeps them in `std::string`s too. A caller can overwrite the output before it frees it, but the copies inside the library stay. Plan: a `monero_utils_free_secret()` that wipes the output with its length, and `memwipe()` from monero-project on the copies that monero-c makes.
- [ ] **monero-c: make the wait for the next block stoppable.** `monero_wallet_wait_for_next_block()` blocks until a block arrives, and neither `monero_wallet_stop_syncing()` nor `monero_wallet_close()` wakes it (tested on regtest: still blocked 8 s after both). `monero_daemon_wait_for_next_block_header()` gives up after 30 minutes. A caller can't cancel either, so a C# task that waits on one keeps a thread until a block comes. Plan: a variant with a timeout in milliseconds, which monero-c can build on `get_height()` and a short sleep, or an interruptible wait in monero-cpp. `wait_for_next_block()` of monero-cpp has two more bugs that the fix there has to cover. It adds its listener and then waits on a condition variable with no predicate, so a block that arrives in between wakes nobody, and `last_height` is not initialized, so a spurious wake-up returns garbage.
- [ ] **monero-c: give the errors a code.** The only result is `MONERO_ERROR` with a message, so a binding that throws typed exceptions (network, invalid argument, not supported) has to match the text. Plan: a `monero_last_error_code()` with a small enum, set from the exception types that `guard()` sees, and keep `MONERO_ERROR` as it is. It adds a function, so it bumps the minor version of the ABI.
- [ ] **monero-c: let the callback structs grow.** `monero_wallet_listener_callbacks` and `monero_daemon_listener_callbacks` have no size field, so a new callback changes the layout, and a caller that was built with the old one makes the library read past its struct. While the major version is 0 the ABI version covers it. Before 1.0, add a `uint32_t struct_size` as the first member, and copy only that many bytes.
- [ ] **monero-c: `MONERO_EXPORT` on Windows when linking the static library.** The header uses `__declspec(dllimport)` unless `MONERO_C_BUILD` is defined, so a program that links `libmonero_c.a` on Windows looks for `__imp_` symbols and fails. Plan: a `MONERO_C_STATIC` define that empties `MONERO_EXPORT`, set as an interface definition of the `monero_c-static` target. Nothing builds or tests the static library on Windows today.
- [ ] **monero-c: hide the static archives' symbols on macOS and Windows.** On Linux `-Wl,--exclude-libs,ALL` keeps the exports to the C ABI: 288 functions. Measured on the `Monero.Native.0.1.0-alpha.1` package of PR #12: the macOS libraries export 19,021 (arm64) and 23,086 (x64) symbols, about 12,000 of them C functions of OpenSSL, and the x64 one also exports the three `monero_crypto_amd64_64_24k_*` assembly helpers (291 `monero_*` symbols instead of 288). macOS binds symbols per library (two-level namespace), so this is less harmful than on Linux, but it widens the ABI. Plan: pass an export list to ld64 with `-Wl,-exported_symbols_list`, as monero-java does for `_Java_*` and `_JNI_OnLoad` in its `CMakeLists.txt`, with `_monero_*`, and check it in CI with `nm -gU`, failing on any export outside the list, as its Build does. The Windows DLL exports the 288 functions and 1,099 Boost template symbols that Boost marks `BOOST_SYMBOL_EXPORT`, and no C symbols of OpenSSL or libsodium, so it is low priority. `tests/c/abi/check_symbols.cmake` runs on Linux only.
- [ ] **monero-cpp: limit the nesting of the JSON it parses.** `deserialize_rpc_response()` parses every response with `gen_utils::deserialize()`, which calls boost's `read_json()`, and that parser recurses once per level. A node that answers a request with 200 KB of `[[[[...` (100000 levels) overflows the 8 MB stack and ends the process. Tested with `monero_rpc_connection_send_json_request()` and `monero_daemon_get_info()` against a script that answers every request with nested arrays: 20000 levels pass and 100000 crash. monero-c limits the JSON that a caller passes to 64 levels, but it can't reach a response, which monero-cpp parses. A thread with a 1 MB stack, which is the default on Windows, crashes with a response of 8 KB: 4000 levels pass and 8000 crash. Plan: throw "Invalid JSON" above a fixed depth in `gen_utils::deserialize()`, and add a test with the fake server of `monero_c_rpc_connection_unit_tests`.
- [ ] **monero-cpp: `get_blocks_by_range()` lists every height first.** The loop `for (height = start; height <= end; height++)` never ends when `end` is `UINT64_MAX`, and it fills a vector with each height before the first request, so a wide range uses all the memory. monero-c refuses a range of more than 100000 blocks (`MAX_BLOCKS_BY_RANGE` in `monero_c_daemon.cpp`). Plan: send the heights in chunks, as `get_blocks_by_range_chunked()` does, and check the end against the height of the chain. Then the limit of monero-c can go.
- [ ] **monero-project: `wipeable_string::split()` takes quadratic time.** `epee::wipeable_string::split()`, which `get_is_old_style_seed()` and `words_to_bytes()` call, appends a word one character at a time, and each append reallocates, copies and wipes the buffer. A mnemonic of 100 KB takes 0.8 s to check and one of 400 KB takes 15 s. monero-c rejects a mnemonic of more than 4096 bytes (`MAX_MNEMONIC_LENGTH` in `monero_c_common.h`), which is far above any valid one. Plan: report it upstream. The limit stays, because it also keeps a megabyte of text away from the check.
- [ ] **monero-c: call the wallet callbacks without the lock of the wallet.** `monero_wallet_full::notify_listeners()` calls the callbacks while a sync holds the lock of the wallet. A callback that calls `monero_wallet_get_balance()`, `monero_wallet_get_unlocked_balance()`, `monero_wallet_get_txs()`, `monero_wallet_get_outputs()` or `monero_wallet_get_accounts()` on its wallet waits for that lock forever, and then `monero_wallet_remove_listener()` and `monero_wallet_stop_syncing()` wait for the callback. Plan: put the events in a queue that a thread of monero-c delivers without any lock, copy the strings, and let `monero_wallet_remove_listener()` and `monero_wallet_listener_free()` wait for the queue unless they are called from a callback. It touches the same code as the listener race items above.
- [ ] **monero-c: wallet paths with non-ASCII characters on Windows.** monero-project activates UTF-8 for Boost.Filesystem on Windows in `Wallet::init()` and in `simplewallet` (`boost::locale::generator().generate("")` and `boost::filesystem::path::imbue()`), and neither monero-cpp nor monero-c does. Plan: run the test on Windows, and if it fails, set the locale once for `_WIN32` in monero-c or in monero-cpp (Boost.Locale is already one of the linked components), then check `monero_wallet_exists()`, `monero_wallet_open()`, `monero_wallet_move_to()` and the logging path.
- [ ] **monero-cpp: make `monero_utils::free()` release the daemon models.** `free(block)` resets `m_block` of the txs in `m_txs`, and of a wallet tx its transfers, outputs, inputs and tx set. Add it next to the other Linux link options, and check the sanitizer builds, where the runtime provides symbols.

- [x] **monero-c: a version of the C ABI.** `monero_utils_get_abi_version()` returns the major, minor and patch versions, which are `MONERO_C_ABI_VERSION_MAJOR`, `MINOR` and `PATCH` in `monero_c_utils.h`, three numbers like the releases of monero-cpp and monero-python. The version is 0.1.0. While the major version is 0, a change of the minor version can break callers. From 1, only the major version breaks callers and the minor grows when functions are added. The patch version changes for fixes that leave the ABI as it is. `monero_c_abi_unit_tests` pins the numbers, so a change of the version is deliberate. The package README tells callers to compare the version after loading the library. Bump the minor version with any change of an enum value, a layout or a signature that the ABI test pins, until 1.0.
