# Thread Safety

> [!WARNING]
>
> Thread safety is incomplete. Some concurrent uses are still unsafe.

What holds today. Each point says where the limit comes from: **[monero-c]** (this library), **[monero-cpp]** or **[monero-project]** (wallet2, epee):

- **[monero-project]** Calls on one `monero_daemon` handle don't run in parallel: the HTTP client of epee, which monero-cpp uses, holds a lock for each request.
- **[monero-cpp]** monero-cpp locks a `monero_rpc_connection`, so one handle can be shared by several threads and by the daemons and RPC wallets created from it.
- **[monero-cpp]** Don't use one `monero_wallet` handle from two threads at once. `monero_wallet_start_syncing()` syncs on a thread owned by monero-cpp, next to the calls on the handle. The exception is `monero_wallet_request_shutdown()`, which makes the calls in flight return, so that a thread can wait for them and then close and free the wallet. _(The full wallet takes its sync lock for some operations only, and wallet2 is not thread safe; monero_c adds no lock of its own on the handle. `monero_wallet_request_shutdown()` is **[monero-c]** exposing `request_shutdown()` of monero-cpp.)_
- **[monero-cpp]** The callbacks of a daemon listener run on a thread owned by monero-cpp. Inside one, `monero_daemon_remove_listener()` and `monero_daemon_remove_listeners()` are safe. Don't free a wallet, a daemon or a daemon listener from a callback. _(The poller thread and the rule about freeing from a callback are monero-cpp's.)_
- **[monero-c]** The callbacks of a wallet listener run one at a time, in order, on a thread of monero_c that the listener owns, with no lock of the wallet held, so a callback can call the wallet. A call that needs what a running sync holds, such as `monero_wallet_get_balance()`, waits until the sync is done, and the sync does not wait for the callback. The wallet puts its notifications in a queue, so a callback comes a short time after the event: a sync progress or a balance that waits is replaced by the newer one, more than 100000 waiting new blocks drop the oldest, and an output is never dropped. `monero_wallet_sync()`, `monero_wallet_scan_txs()`, `monero_wallet_rescan_blockchain()` and `monero_wallet_close()` return after the callbacks they caused have returned, no callback of a listener starts after `monero_wallet_remove_listener()` returns, and a callback can remove or free its own listener. A callback that does not return holds those calls. A daemon callback runs on a thread of monero-cpp and can call the daemon. _(The queue and the thread of the listener are monero_c's. The wait for a running sync is **[monero-cpp]**: its sync lock.)_
- **[monero-c]** Different listeners on one daemon can be managed from different threads, and `monero_daemon_get_listeners()` can run meanwhile. The handles that it returns are the ones that were added at that moment, and a thread must not free a handle of another. _(The list of handles is kept by monero_c.)_
- **[monero-c]** One listener can be on one wallet at a time. Adding it to a second wallet fails.
- **[monero-c]** A binding avoids the races of adding, removing and freeing a wallet listener by keeping one native listener per wallet and fanning out to its own listeners. It adds the native listener once, when the first of its own arrives, and doesn't remove it. It frees it after `monero_wallet_close()` has returned, which waits for the callbacks in flight, and then frees the wallet. monero-java works this way. _(It is a workaround for the listener API of monero_c, which doesn't make add, remove and free atomic.)_
- **[monero-c]** `monero_daemon_wait_for_next_block_header()` blocks only its calling thread, and other calls on the handle run meanwhile. Neither it nor `monero_wallet_wait_for_next_block()` can be cancelled (**[monero-cpp]**: their waits have no way out), so a program that has to stop uses `monero_daemon_wait_for_next_block_header_timeout()` and `monero_wallet_wait_for_next_block_timeout()`, which return after the timeout with `out_timed_out` set, and waits again unless it was cancelled.
- **[monero-c]** `monero_last_error()` and `monero_last_error_code()` are per thread: they return the last error of the calling thread. The code comes from the type of the exception that ended the call: `MONERO_ERROR_INVALID_ARGUMENT` for what monero_c checks (a NULL pointer, a value out of range, a JSON or a text that doesn't parse, and the `validate_` functions), `MONERO_ERROR_OUT_OF_MEMORY`, `MONERO_ERROR_RPC` for an error that the daemon or the wallet RPC server answered with, and `MONERO_ERROR_IO` for a system error of a file or a socket. What monero-cpp reports as a plain error, a network failure included, is `MONERO_ERROR_GENERIC`, and a binding keeps the message for it. _(The per-thread state and the codes are monero_c's. That the errors of the network and of monero-cpp come as plain errors is **[monero-cpp]**.)_
